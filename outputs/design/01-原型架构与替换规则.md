# 统一原型架构与替换规则

无论 M0 选 A/B/C，第一段 Godot 原型都按本文构造。设计目标是：玩法先可玩、占位可换、内容可数据化、美术替换不碰玩法代码。

## 1. 固定技术决策

- 引擎：本机已找到 Godot 4.7.2 stable，使用控制台版：
  `F:\Godot\4.7.2\Godot_v4.7.2-stable_win64_console.exe`
- 项目形态：Windows 本地运行，日后导出 Steam Windows 版；不先做移动端。
- 版本管理：每完成一个里程碑打 tag，稳定版本再考虑推远端。
- 数据优先：房间、敌人、道具、能力、文本尽量以 Resource/JSON 定义，避免把内容写死在 Player 脚本里。

## 2. 镜头与输入基线

### 2.1 镜头

以本机 Crypt Custodian 可运行版本为唯一对照，不以图片猜测。M1 需要记录：

- 相机 Yaw/Pitch
- 相机 FOV
- 相机高度与跟随距离
- 玩家处于画面中的位置
- 快速移动时的相机顺滑/延迟参数
- 跳跃、冲刺、翻滚、攻击的持续时间和位移曲线

验收标准是“同屏对比下，两个版本的基本操作映射相同；不要求复制原版素材或代码”。

### 2.2 键位基线（M1 冻结前为临时表）

从本地配置文件与汉化文本读到的动作类别包括：移动、跳跃、攻击、冲刺、翻滚躲避、互动/查看地图、确认/取消。默认按键是 WASD 类移动 + Space/鼠标左键/E 类动作键 + Esc 暂停/取消。

正式表将在 M1 打开参考版“设置 -> 控制”页后逐项冻结，并写进 `docs/control-baseline.md`，不会凭网络资料拍脑袋。

### 2.3 输入命名规范

Godot InputMap 动作一律使用语义名，不绑定键位：

```text
move_up/move_down/move_left/move_right
jump
attack
dash
dodge
interact
special
map
pause
confirm
cancel
```

键位做成一个 `input/default_input.tres` 或 Godot 默认 InputMap 资源，方便与参考版 1:1 对照。

## 4. 占位替换契约

所有未来要替换的视觉资产都遵守：

1. 玩法场景只引用 `ArtHost` 节点；Godot 场景树里视觉子树全部挂在 `ArtHost` 下。
2. `ArtHost` 只负责展示，不承载伤害判定、移动、重力、动画状态机等玩法逻辑。
3. 占位模型使用 Box/Capsule/Cylinder 或 PrismMesh，并命名 `art_key_*`，例如 `art_key_player_body`、`art_key_broom`、`art_key_ghost_a`。
4. 最终美术是另一个同构 `ArtHost` 场景，导出 `art_key` 与资源路径，由内容表把“艺术资源 key”替换到角色/房间上。
5. 碰撞盒、受击盒、移动脚印属于玩法层，和最终模型尺寸解耦；避免出现“换模型后碰撞突然不对”的问题。

占位原则：

- 占位造型要能表达“位置、朝向、攻击范围、受击状态”，不需要漂亮。
- 动作变化使用夸张的 Tween/Scale 占位，后续原画/动画轮次再补细节。
- 每个新房间先画一张黑白拓扑/示意图，通过确认后再进 Godot。

## 5. 首段可运行模块

M1 最小模块：

```text

  Player3D           # CharacterBody3D + 输入状态机
  TestRoom           # 地板、墙、门、装饰位

  HudMock            # 生命/道具/提示占位
```

```text

```

## 6. 后续大模块的抽象边界

- `RoomRuntime`：负责房间内生成、门连接、清场事件、机关反馈；只关心数据里的 RoomDef。
- `RunDirector`：负责“这一局/这一班”的房间顺序与奖励；A/B/C 选定后只是替换这个导演的规则。
- `BuildSystem`：负责 Isaac 式道具池、叠加与 synergy 的数值注册，第一版不急着做大量道具。
- `GateProgression`：负责 HK 式能力门、地图标记、可返回路线；先做“锁-钥匙-回来”的最小演示。
- `ComedyDirector`：负责物理喜剧与送客演出，预留为独立模块，不在 M1 写死。

本文件在选定方向后会继续修订为正式技术方案。

### A+ 方向的架构补充

若确认《五星除灵》，后续架构在以上基础上增加两个高层模块，不在 M1 实现：

- `RouteLayer`：夜班城区、派单路线、现场连接、快穿与能力门解锁，输入/镜头可以先做成轻量快穿验证。
- `CaseRuntime`：基于 RoomRuntime 的“上门清场”，负责投诉目标、闹事组合与好评结算。

路线与现场之间通过 GameSession 里的“派单数据”互相读取，不互相持有美术节点。
